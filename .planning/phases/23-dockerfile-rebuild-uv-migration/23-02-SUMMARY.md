## Decisions Made

- **Compile inside scipy-notebook (not standalone uv image):** The plan's literal Step 2 command (`docker run ghcr.io/astral-sh/uv:0.11.8 pip compile ...`) failed because the standalone uv image is a scratch base with no libc-detection helpers (`/bin/sh`, `/usr/bin/env`, `/bin/dash`, `/bin/ls` all absent). uv 0.11.8 cannot discover managed Python installations without those probes. Switched to the Phase 22-proven approach: run uv inside scipy-notebook:2026-04-27 via the curl installer. Functional equivalence preserved because `--python-version 3.14` forces the resolution target explicitly — marker evaluation is identical regardless of which container hosts uv. See Deviations §1.
- **Lockfile package count is 111 (root has 100):** Template adds explicit deps (e.g., `pyinstaller`, `nbconvert`, `nbformat`, `jinja2`, `pytest`, `plotly`, `kaggle` all in template requirements.in) that root resolves transitively or doesn't need. 11-package delta is expected.
- **Hash count 1618 vs root's 1644:** Slight under-count vs root because template lacks `fastapi`/`uvicorn`/`onnxruntime` in its requirements.in (root has them transitively via deployment tooling). 1618 still well above the 1000 floor specified in plan acceptance criteria.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Compile rig: scipy-notebook + curl-installer (not standalone uv image)**
- **Found during:** Task 1 Step 2 (regenerate the lockfile)
- **Issue:** Plan's literal Step 2 command runs `docker run ghcr.io/astral-sh/uv:0.11.8 pip compile requirements.in --python-version 3.14 ...`. uv 0.11.8 in the standalone image fails with `error: Failed to discover managed Python installations / Caused by: Failed to find any common binaries to determine libc from: /bin/sh, /usr/bin/env, /bin/dash, /bin/ls`. The standalone uv image is a scratch base shipping only the uv binary — it lacks the probe binaries uv uses to detect glibc vs musl before downloading a managed Python. Setting `UV_PYTHON_DOWNLOADS=automatic` did not help (libc detection runs before the download attempt).
- **Fix:** Switched to the Phase 22-proven compile rig: `docker run --rm --entrypoint bash -v $(pwd)/.claude/doml/templates:/work --user root quay.io/jupyter/scipy-notebook:2026-04-27 -lc 'curl -fsSL https://github.com/astral-sh/uv/releases/download/0.11.8/uv-installer.sh | env UV_INSTALL_DIR=/tmp/uvbin sh > /dev/null 2>&1 && /tmp/uvbin/uv pip compile requirements.in --python-version 3.14 --generate-hashes -o requirements.txt'`. scipy-notebook ships glibc + cp313 + cp314 conda Python, so libc detection succeeds, and `--python-version 3.14` still pins the resolution target identically.
- **Files modified:** `.claude/doml/templates/requirements.txt` (output identical to what the literal plan intended — `head -2` shows the same `uv pip compile requirements.in --python-version 3.14 --generate-hashes -o requirements.txt` recorded command)
- **Verification:** `head -2 .claude/doml/templates/requirements.txt` shows `# This file was autogenerated by uv via the following command: # uv pip compile requirements.in --python-version 3.14 --generate-hashes -o requirements.txt` — same shape as Phase 22 root's lockfile header. Hash count 1618 ≥ 1000 floor. Resolution targeted Python 3.14 as specified.
- **Committed in:** `5ea0776` (the corrected output is the only thing committed; the script-level fix is documented here for future audit reproducibility)
- **Functional equivalence rationale:** `uv pip compile` resolves dependencies from PyPI metadata only — it does NOT touch local conda site-packages or the runtime Python interpreter when `--python-version` is set explicitly. The marker evaluation (`python_version`, `platform_machine`, `os_name`, `sys_platform`) depends on flag values + uv's internal environment model, not on the container's Python runtime. Therefore compile-inside-scipy-notebook produces byte-identical output to compile-inside-standalone-uv-image (when both work). This is also why Phase 22 used scipy-notebook directly for compile — same pattern.
